# 升级与回滚核心

`boot.c` 管理两个镜像槽的启动决策，使用独立的双副本元数据存储，不能与参数区、事件日志或镜像槽重叠。元数据写入先擦除目标副本，再写入并回读主体，最后写提交标志并回读；发生 I/O 错误后必须重新读取状态，不得假定写入一定未生效。两个副本均损坏时拒绝启动决策；仅允许可信工厂流程在两个记录区域均为 0xff 时初始化。

升级流程：下载器只写入非活动槽，并完成完整镜像写入；`tp_boot_stage` 校验镜像后记录候选版本。下次启动再次校验候选镜像，先持久化试运行状态，再选择候选槽。应用完成健康检查后调用 `tp_boot_confirm`；如果再次复位前没有确认，启动器验证并恢复原确认镜像。候选无效时也恢复原镜像；读取或校验设备 I/O 失败则不选择镜像。所有操作需要单一所有者串行执行，下载器不得同时改写正在验证或启动的镜像。

调用方的 `verify_image` 必须验证完整镜像边界、产品兼容性、版本、签名和完整性，并区分镜像无效与设备 I/O 故障。启动接口尚未接入签名校验，也缺少公钥保护、Flash 布局、固件跳转及硬件适配；本模块不能单独构成安全 Bootloader。元数据 CRC 只检测意外损坏，版本比较不能防止攻击者回滚元数据；防恶意回滚需要可信的不可回退版本存储。设备应用应在充分自检后确认镜像，不能启动即确认。

主机测试模拟了元数据写入各步骤发生错误、提交已生效但回读失败、候选镜像损坏、校验 I/O 失败和未确认复位。闪存擦除粒度、电源故障特性及实际密钥保护仍需目标硬件验证。

`download.c` 提供顺序分块下载和断点恢复：先持久化擦除状态，再擦除目标槽；每块写入并回读后更新偏移；完整镜像通过调用方校验后才标为 VERIFIED。元数据使用独立双槽，与启动状态和镜像区域隔离。调用方必须确认目标槽既非活动镜像也非已暂存镜像，并提供可信清单；当前接口没有自动检查启动状态或自动调用 `tp_boot_stage`。

写入报错后必须重新读取偏移，若偏移没有前进，须以完全相同的偏移、长度和数据重试；底层必须支持对已部分写入的相同内容重复编程。首次元数据提交中断可能导致两槽均无有效记录且不全为空，此时拒绝继续，需由可信维护流程检查并恢复；当前没有取消下载或恢复损坏元数据的接口。实际 Flash 对重复编程和擦除的支持以及硬件传输尚未验证。

`upgrade.c` 将下载与启动状态串联：开始、恢复和写入时要求启动状态空闲、目标槽非活动槽且版本递增；结束时完成下载校验，再由启动模块独立校验并暂存。若暂存提交成功但回读报错，重试结束操作可识别已暂存的相同槽和版本。上述检查和实际读写之间要求所有启动、下载和升级操作由同一所有者串行执行，不能绕过协调层并发调用底层修改接口；重启时还需按同一约束安排启动决策。清单认证和容量检查仍由调用方负责。

`tp_upgrade_command_execute` 为串口或网络适配层提供完整消息级命令处理：STATUS 查询下载状态；BEGIN 将清单原文交给认证回调，通过后开始；RESUME 恢复中断的擦除；WRITE 接收四字节小端偏移和最多 256 字节数据；FINISH 校验并暂存。STATUS、RESUME、FINISH 不带数据，WRITE 至少携带一个数据字节。回复包含操作结果和可选的持久化下载状态；操作结果表示命令结果，`state_available=false` 表示本次状态读取未成功，STATUS 本身返回状态读取结果。传输层负责分帧、长度限制、完整性校验、响应编码、超时和访问控制；本接口不直接收发字节流。

`tp_upgrade_wire` 提供可用于字节流的参考帧层：帧以 `7e` 开始和结束，内容中的 `7e`/`7d` 编码为 `7d` 后接原字节异或 `20`。解码内容依次为版本 `01`、命令、16 位请求序号、16 位数据长度、数据和 CRC-16/Modbus，整数均小端；CRC 覆盖版本到数据，数据最长 512 字节。响应命令为请求命令或 `80`，其数据为结果码、状态有效标志；状态有效时依次附加阶段、槽号、版本、镜像大小、已写偏移（后三项均 32 位小端）和 32 字节清单 ID。序号仅用于匹配回复，不防重放。无效长度、转义或 CRC 不执行命令，不发响应，下一帧分隔符恢复同步。

串口任务逐字节调用 `tp_upgrade_wire_byte`，串口错误或接收超时时调用 `tp_upgrade_wire_reset` 并等待新帧；发送回调在返回前复制完整帧。命令执行和发送可能阻塞，使用专门的升级任务并串行化访问；若发送失败，操作仍可能已生效，应查询状态确认。发送方应限制清单大小并按序等待应答，现场仍需实现 UART 或网络收发及丢包重试。帧 CRC 不提供认证、保密或抗重放，升级接口的访问控制、可信清单和镜像验证由系统提供。帧处理使用数百字节栈空间，实际线程栈需测量。

`../tools/upgrade_client.py` 是 Python 3 参考发送端，支持 TCP 和串口（串口需要安装 `pyserial`）。例如：

```text
python freertos/tools/upgrade_client.py --tcp 127.0.0.1:9000 --manifest manifest.bin --image firmware.bin
python freertos/tools/upgrade_client.py --serial COM3 --baud 115200 --manifest manifest.bin --image firmware.bin
```

发送工具使用 TPU1 清单，自动计算与设备认证回调一致的 32 字节 ID，并在连接设备前核对本地镜像大小及摘要。工具在超时后查询持久化状态，并只在 ID、大小与预期一致时继续；设备仍须验证签名及接收到的镜像。超时可能发生在设备已执行操作后，连接中断时重新运行并核对设备状态；首次 BEGIN 和其他错误不保证可自动恢复。TCP 为明文，实际网络需要安全传输和访问控制。设备侧已有 USART2 接收参考，TCP 设备接收与端到端实机测试尚未完成。

断线或写入结果不确定时先查询持久化偏移：偏移已前进表示该块已提交，否则以相同内容重传；如果查询失败，不能推测是否写入。FINISH 可以重试。认证回调必须验证签名及产品兼容性、槽容量，并生成与可信清单绑定的持久化 ID；下载和启动时的镜像校验必须独立验证完整性及真实性，不能把 CRC、传输完整性或清单 ID 当作签名。该接口的单元测试认证回调只是替身；签名验证、F407 串口接收和 Flash 控制器已有参考实现，独立启动器参考工程见 `../firmware_boot/README.md`，板级装配和实机验证仍待完成。

主机联通测试通过共享库将 Python 发送端连接到 C 帧处理、升级和启动核心，覆盖丢失应答、断线续传、拒绝清单和损坏镜像。测试使用内存存储和固定内容的认证与镜像校验替身，不验证真实签名或设备。构建时检测到 Python 解释器后，`ctest --test-dir build --output-on-failure` 会运行该测试；也可设置 `TP_UP_SIM_LIB` 为构建出的 `upgrade_simulator` 共享库绝对路径后运行 `python -m unittest discover -s tests -p test_upgrade_interop.py -v`。

`tp_upgrade_stream` 为单连接提供字节流会话：按接收时刻检查帧间超时，在空闲时轮询超时，并在串口溢出、断线或连接切换时复位。接收事件和空闲轮询必须按时间顺序交付；带时间戳的队列应先排空再按当前时间轮询。计时器使用 32 位毫秒回绕运算，超时上限为 2^31-1 毫秒。发送回调仍须完整复制或发送响应；超时与断线不能撤销已执行的升级操作。实际 UART/网络收发、任务调度、访问控制和存储仍需接入。
`tp_image_sha256` 使用 TinyCrypt v0.2.8 以 256 字节缓冲区分块计算指定镜像的 SHA-256；`tp_image_sha256_verify` 比较完整摘要。调用方提供镜像读取回调和每个槽的容量，长度为零或超出槽容量时拒绝读取，读取失败原样返回。摘要必须来自已认证的清单，且校验期间禁止并发擦写。该组件可通过下述签名清单接入 `tp_download_io.verify`，尚未接入 `tp_boot_io.verify_image`；仅使用哈希不能证明镜像来源，完整安全启动还需要签名认证、可信密钥和受保护的镜像布局。
`tp_signed_manifest` 定义参考二进制清单：前 52 字节依次为 `TPU1`、产品 ID/版本/镜像大小（各 32 位小端）、槽号（1 字节）、三个零字节和镜像 SHA-256；后 64 字节是针对前 52 字节 SHA-256 的 P-256 ECDSA 签名 `r || s`（各 32 字节大端）。配置可信公钥（无前缀的 `x || y`）、产品 ID、槽容量和读取回调后，可将 `tp_signed_manifest_authenticate` 接入命令认证，将 `tp_signed_manifest_verify_image` 接入下载校验；其他存储回调须通过同一 `image_ctx` 适配。清单 ID 是前 52 字节的 SHA-256。验证成功后缓存摘要和身份，设备重启后应再次发送同一 BEGIN 清单以重新认证，然后再完成下载；升级客户端会先发送 BEGIN，并可根据持久状态继续。清单持久化、公钥保护和产品身份配置需由部署系统提供。启动模块可使用下述独立验签接口，不能仅依赖下载时的缓存。

## 主机签名工具

安装 Python `cryptography` 后，使用 P-256 PEM 私钥生成清单：

```text
python tools/sign_manifest.py --image firmware.bin --key signing-key.pem --product 0x12345678 --version 2 --bank 1 --output manifest.bin
```

加密 PEM 私钥时增加 `--encrypted-key`，工具会交互式读取密码。输出的 Manifest ID 是签名正文的 SHA-256；发送工具自动计算该 ID，也可用 `--manifest-id` 指定期望值进行核对。发送前工具检查 TPU1 清单字段、镜像大小和 SHA-256，检查通过不代表签名有效，设备仍须独立验签；`--manifest` 和 `--image` 分别传入生成的清单与原镜像。工具不会覆盖已有输出文件；产品 ID、版本和目标槽必须与设备配置和升级策略一致。私钥只保存在可信签名环境，设备仅使用对应公钥；测试密钥不能用于实际部署。工具生成清单不表示设备已完成启动验签或硬件升级。

## 每槽清单存储与启动验签

`tp_signed_boot` 将签名清单存储到与镜像槽对应的两个独立可擦写槽，槽大小至少 120 字节，前 116 字节是清单，末尾 4 字节是最后提交标记。配置可信公钥、产品 ID、镜像读取和容量，再将 `tp_signed_boot_authenticate`、`tp_signed_boot_download_verify` 和 `tp_signed_boot_verify` 分别接入升级命令、下载验证和启动验证回调。下载验证先检查完整镜像，再擦写并回读清单，最后提交；启动验证每次重新读取清单，独立验签并计算镜像哈希，不依赖下载时的 RAM 缓存。各存储回调的上下文不同，下载的擦写接口需要由装配层适配到同一个 `image_ctx`。

所有镜像、清单、下载及启动状态必须由同一个执行者串行管理，清单槽不能与镜像、启动和下载元数据重叠；仅允许更新非活动且非暂存槽。首次可信生产初始化必须分别烧录镜像与相应有效签名清单，再配置启动元数据。发生擦写或回读错误后必须重新读取状态；提交标记可能已生效，重试会识别相同记录。启动验证到镜像执行之间也必须禁止改写镜像和清单。实际板级 Flash 装配、密钥保护和防恶意回滚仍需完成；独立启动器参考工程已接入启动跳转，本存储层尚未装配到默认业务固件。

当下载已验证但启动暂存尚未完成时，重复 BEGIN 同一清单返回 BUSY 且保留镜像；客户端随后读取进度并继续 FINISH。已验证的不同清单仍可开始新下载，但协调层必须确认目标槽和版本符合升级策略。


## 升级组件装配

`tp_secure_upgrade_init` 以长期有效的配置组装签名认证、每槽清单、镜像读写、下载与启动元数据和命令入口。调用方提供三个互不重叠的双槽存储、两个镜像槽的读写擦除回调与容量、产品 ID 和可信公钥，初始化后可将 `commands` 交给 `tp_upgrade_wire` 或 F407 升级串口任务；`boot` 用于启动选择与试运行确认。初始化不会格式化存储、烧录工厂镜像或自动启动传输。对象包含内部指针，初始化后不能移动或复制，生命周期内必须单一所有者串行调用。

主机集成测试使用临时生成的 P-256 私钥，从 Python 签名工具和升级客户端走真实的 C 协议、下载、清单持久化和启动验证；覆盖中断后重新认证、试运行确认与未确认回滚、签名及镜像篡改。依赖 `cryptography`，CMake 找到该依赖时自动注册测试。测试存储是内存替身，不代表目标 Flash 的掉电和擦写行为。
### 升级专用 FRAM 参考布局

`tp_upgrade_fram` 为升级记录提供三个独立的双槽存储：启动状态 0–255、下载状态 256–511、签名清单 512–767，每槽 128 字节。通过 `tp_upgrade_fram_init` 初始化，再分别用 `tp_upgrade_fram_store(&fram.boot)`、`tp_upgrade_fram_store(&fram.download)`、`tp_upgrade_fram_store(&fram.manifests)` 填入 `tp_secure_upgrade_config` 对应的三个存储接口。FRAM 对象和 I²C 上下文必须存活至升级与启动操作结束，调用方须串行化访问。擦除先清除该记录的提交标记，再填充 `0xff`；记录格式或提交标记位置发生变化时必须同步修改适配器。

此布局占用一颗专用 MB85RC16 的前 768 字节。原配置与事件日志已占满另一颗 MB85RC16；两颗器件均占用地址 `0x50..0x57`，因此必须使用独立 I²C 总线或可隔离通道的总线复用器。独立启动器参考工程已使用此布局；板级总线和可信密钥仍需装配。测试使用 I²C 内存替身及故障注入，实际供电和掉电行为尚未验证。

### 启动目标检查

`tp_boot_target_prepare` 将启动状态选择与镜像向量检查串联。验证回调必须认证所选槽、版本和完整镜像并返回认证过的镜像长度；可使用 `tp_signed_boot_verify_size`。检查首个向量中的初始栈指针是否位于配置的 RAM 范围（允许指向范围末端）、是否按 8 字节对齐；复位入口必须为 Thumb 地址，且目标指令的前两个字节位于认证过的镜像长度内。槽地址、容量、向量表对齐和 RAM 范围由板级可信配置提供。两个槽不得重叠。候选镜像检查失败时使用启动状态机回退，I/O 错误则拒绝选择；准备结果写出前，试运行状态必须已经持久化。

检查只覆盖初始栈和复位入口，不逐项验证中断向量，也不执行跳转。验证、状态持久化和使用结果之间必须禁止镜像写入，并由单一所有者串行执行；F407 参考交接接口见 `../firmware/README.md`；独立启动器参考工程已调用该接口，仍需完成板级初始化、可信密钥存放及实机验证。

### 可信工厂初始化

`tp_factory_provision` 用于可信、单一所有者的生产初始化：调用方预先将镜像写入对应槽，配置 `tp_signed_boot` 的可信公钥、产品 ID、镜像读取和独立清单存储，并提供独立启动元数据存储及完整签名清单。函数先认证清单，检查两个启动记录区域为空白，验证已有镜像，再提交清单与启动状态；不会擦写镜像。已经完成且清单完全相同的初始化可重试，函数重新检查签名和镜像后返回成功；已存在其他有效启动状态返回 `TP_BUSY`，损坏或部分写入的启动记录返回 `TP_INVALID`，不自动格式化。发生 I/O 错误后应重新读取和重试，不能假定写入结果。

此接口没有暴露到普通升级命令或默认启动入口，须由受控生产工具或专用生产固件调用；不负责密钥生成、保护、Flash 烧录或受损元数据的恢复。工厂恢复需在可信环境确认设备状态后另行执行。主机测试使用真实 P-256 签名和内存 FRAM 替身，逐次注入部分写入失败并检查重试与启动选择；未验证实物掉电。

### 应用试运行确认门控

`tp_trial_confirm` 为应用提供确认前的健康观察窗口。使用 `tp_trial_confirm_init` 配置启动状态接口、可信运行槽、稳定时间和最大采样间隔；周期性调用 `tp_trial_confirm_poll`，只有试运行槽与运行槽一致且健康样本持续满足配置窗口时，才调用 `tp_boot_confirm` 再次验签并提交。健康失败、I/O 错误或采样间隔过长会重新开始观察；确认提交后的读回失败可能已经提交，下一次调用会重新读取持久状态。已确认的活动槽返回成功，槽不一致或启动状态不符合预期则拒绝。计时基于 32 位毫秒时钟并支持回绕，调用间隔须小于 2³¹ 毫秒。

健康值必须由应用自检及任务进度等实际条件生成，且需要反映两次采样间锁存的故障；仅凭看门狗启动宽限期不能认定所有功能已正常。调用方必须保证运行槽来源可信、镜像不可并发修改，并串行化升级存储和确认操作；认证可能耗时，不能放在实时控制任务或临界区。此门控目前是可调用核心，尚未接入默认业务入口或选择实际自检策略；失败后由系统复位触发启动器回滚。主机集成测试覆盖真实签名镜像确认，以及故障、间隔和不确定写入处理，未代表目标设备运行。


### FreeRTOS 试运行确认任务

`tp_freertos_trial_start` 在调度器启动前创建任务，使用 1 kHz、至少 32 位 tick；应用应配置低于实时控制任务的优先级。调用方须提供与升级操作共用的非阻塞存储锁、反映采样间锁存故障的非阻塞健康快照、完成回调，以及持续有效的任务对象和上下文。锁不可用、健康异常或存储错误会中断健康计时；超时和运行槽不匹配由完成回调处理，例如采取安全状态并复位以触发回滚。超时在每次轮询前检查，不能中断正在执行的存储访问或签名验证；健康快照也不能证明验签期间的状态。已有确认状态且运行槽匹配时，核心门控会直接返回成功。

适配器尚未装配进默认业务入口，实际运行槽、共享锁、自检策略、可信身份和失败处理仍须由板级应用提供。未进行上板验证。

串口升级可通过 `tp_f407_upgrade_uart_init_shared` 使用与试运行确认相同的非阻塞存储锁。锁忙时请求得到 `TP_LOCK_BUSY`，可由发送端重试；成功获取锁后，完整命令（包括状态读取）串行执行，并在发送回复前释放锁。旧的初始化接口仍要求升级任务独占所有相关存储和镜像操作；使用共享锁也要求其他访问者遵循同一把锁，尚需在业务入口实际装配。

`tp_f407_upgrade_init` 将独立升级 FRAM、F407 双槽 Flash 和签名升级核心组合起来；它要求由可信代码提供当前 VTOR，并检查该槽与启动记录一致（试运行时对应候选槽），防止擦写当前运行镜像。可将其 `secure.commands` 交给共享锁串口接口，将 `secure.boot` 交给试运行确认任务。此组件只提供装配接口：板级还须提供隔离后的 FRAM 总线、可信产品身份与公钥、相同的共享锁，以及单 Bank Flash 擦写前的安全输出和看门狗策略。此组件尚未接入默认业务入口。

串口共享锁繁忙使用结果码 `TP_LOCK_BUSY`（数值 5），表示命令尚未执行；客户端默认最多重试 20 次，间隔 100 ms，每次使用新序号。普通 `TP_BUSY` 不作自动重试，因为可能代表已有升级状态。旧版客户端需要更新才能识别结果码 5。响应超时仍按原有流程查询持久化进度，不能认定命令未执行。
